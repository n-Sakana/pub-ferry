# 実装計画 — 光学ファイル転送の実用化

対象リポジトリ: `decimen-optical-transfer`（fork）
上流: `bashalarmistalt/decimen-optical-transfer` @ `29cba8f`（v0.3.0）

この文書は「何を作るか」と「なぜその形か」を決める。設計の詳細と脅威境界は
[ARCHITECTURE.md](ARCHITECTURE.md)、実行結果は [RESULTS.md](RESULTS.md)。

---

## 1. これは何で、何ではないか

**これは一回転送のツール**である。指定したファイル、または指定したフォルダ一式を、
光学経路（画面 → カメラ／2次元コードリーダー）で一度だけ相手へ渡す。

**対象外**（実装しない、UI にも出さない）:

- 差分同期、監視同期
- 削除の伝播
- 競合解決、双方向マージ
- 継続的なミラーリング

上流は「1ファイルまたは1テキストを画面とカメラで渡す」ところまでを持っている。
本作業はそこへ **フォルダ一式**、**PC デスクトップアプリ**、**スマホ中継**、
**Tailscale 越しの受け渡し**、**headless 受信**を足す。

---

## 2. 端末の構成と実現する流れ

```
        ┌──── 系統1（Tailscale 内）────┐          ┌──── 系統2（Tailscale 外）────┐
        │  Windows デスクトップ        │          │                              │
        │  Windows ノート              │          │   Windows ノート / デスクトップ │
        │  Linux VPS (headless)        │          │                              │
        └──────────────┬───────────────┘          └───────────────┬──────────────┘
                       │ Tailscale (HTTP + 認証)                  │ 光学 (QR)
                       │                                          │
                  ┌────┴──────────────────────────────────────────┴────┐
                  │            スマートフォン（PWA / 中継器）           │
                  │   Tailscale 内。両系統の間だけをつなぐ              │
                  └───────────────────────────────────────────────────┘
```

### 流れ A: 系統1 → 系統2

1. 系統1 の PC / VPS で送りたいファイル・フォルダを **送信待ち（outbox）** に置く。
2. スマホ PWA が Tailscale 経由でそれを受け取る。
3. スマホが噴水符号の連続 QR を表示する。
4. 系統2 の PC アプリがカメラ（内蔵／Web カメラ）で読み取り、検証して指定フォルダへ保存する。
   - カメラが無い端末向けに、**2次元コードリーダーで一枚ずつ読む低速モード**を別に持つ。

### 流れ B: 系統2 → 系統1

1. 系統2 の PC アプリでファイル・フォルダを選び、連続 QR を表示する。
2. スマホ PWA のカメラで受け取る。
3. スマホが Tailscale 経由で、**登録済みの受信先**（系統1 の PC / VPS）へ送る。
4. 受信先が検証して保存する。

## 3. 上流資産の扱い

上流の光学エンジンは壊さない。**ワイヤーフォーマットは 1 バイトも変えない。**

| 上流モジュール | 扱い |
|---|---|
| `shared/fountain.ts` | そのまま。LT 符号・soliton 分布・`dlog` は wire format |
| `shared/protocol.ts` | そのまま。20 byte フレームヘッダ、`DCF2` コンテナ |
| `shared/frame-capacity.ts` | そのまま |
| `shared/qr-raster.ts` `display.ts` `progress.ts` `worker-pool.ts` `no-signal.ts` `platform.ts` `format.ts` | そのまま |
| `send/` `receive/` `home/` | 既存ページは触らない（PWA として残す） |
| `tests/*.test.ts` 74 件 | 全件維持。ゴールデンベクタも維持 |

**拡張の入れ方**: フォルダ一式は、上流の `packFile(name, type, bytes)` に
`type = "application/vnd.decimen.bundle+dcb1"` の 1 バイト列として渡す。
つまり **新しい payload 種別**であって、新しいフレーム形式ではない。
上流の受信器がこの stream を受けても「知らない種類のファイル」として
SHA-256 検証まで正しく通り、中身の展開だけをこちらが引き取る。

バージョンは manifest 内の `v` と media type の `+dcb1` の二重に持つ。

## 4. 作るもの

### 4.1 共有コア（TypeScript / `shared/`）

| 新規モジュール | 役割 |
|---|---|
| `shared/relative-path.ts` | 相対パス 1 本の検証。traversal・絶対パス・ドライブ文字・UNC・予約名・制御文字・末尾ドット/空白・空セグメント・長さ |
| `shared/bundle.ts` | `DCB1` バンドル。manifest（相対パス／件数／総サイズ／個別サイズ／SHA-256）＋ 本体連結。pack / parse / 検証 |
| `shared/slow-frames.ts` | 一枚ずつ読む低速モード `DCS1`。テキスト安全な枠に frame index / total / CRC-32 を持つ。重複排除・欠落検出 |
| `shared/relay-contract.ts` | Tailscale 中継 API の型・パス・上限 |
| `shared/relay-auth.ts` | ペアリングと HMAC-SHA256 署名／検証（Web Crypto、Node と ブラウザ両方で動く） |
| `shared/design/tokens.css` | design token（色・余白・文字・角丸・影・寸法） |
| `shared/design/base.css` | token だけで書かれた共通コンポーネント |

### 4.2 headless 受信ホスト（Node / `relay/`）

VPS と Windows で **同じ実装**を使う。役割は「受信先」と「送信待ちの置き場」。

- `relay/server.ts` — HTTP サーバ。Tailscale アドレスにだけ bind
- `relay/store.ts` — 受信ルートの登録簿、outbox、一時領域、原子的確定
- `relay/config.ts` — 設定の読み書きと検証。不備は理由付きで **起動失敗**
- `relay/cli.ts` — `pair` / `route add` / `outbox add` / `serve` / `status`
- `relay/systemd/decimen-relay.service` — VPS 常駐用

### 4.3 PC デスクトップアプリ（`pc/`）

系統1 / 系統2 で **同じ**アプリ。参照2製品と同じ層構成に揃える。

```
pc/decimen.bat      薄い起動口（ワンクリック）
pc/decimen.ps1      起動・構成・ビルド・ログのオーケストレーション
pc/src/*.cs         C# ホスト（WPF ウィンドウ + WebView2）
pc/app/             Web 側（共有 TS/CSS を使う画面）
pc/lib/             WebView2 アセンブリ（取得スクリプトで用意、git 管理外）
```

C# ホストの責務:

- ファイル／フォルダ選択ダイアログ
- フォルダ走査 → バンドル生成（相対パス・SHA-256・上限）
- 受信バンドルの検証と安全な保存（一時領域 → 原子的確定、重複名回避、上書きは明示のみ）
- `getUserMedia` の許可制御（信頼オリジンにのみ許可）
- 2次元コードリーダー入力アダプター（COM シリアル／キーボードウェッジ）
- ログ（秘密とファイル本文を書かない）

Web 側の責務:

- 画面。送る／受け取る／設定の 3 つ
- カメラ映像の取得と QR デコード（上流の worker pool をそのまま使う）
- QR 生成と表示（上流の sender をそのまま使う）

### 4.4 スマホ PWA（`relay/` ページ）

上流サイトに 4 ページ目を足す。スマホ幅専用レイアウト。

- 受信先の登録（ペアリングコード / 短寿命トークン）
- 系統1 から受け取る → QR で流す
- カメラで受け取る → 登録済み受信先へ送る

**スマホから PC のファイルシステムは一切見せない。** 見えるのは
「PC/VPS 側でローカルに登録された受信ルートの、分かりやすい名前」だけ。

## 5. プロトコル

### 5.1 `DCB1` バンドル（フォルダ一式）

```
"DCB1"            4 byte  magic
u32               manifest の byte 長（little-endian）
manifest          UTF-8 JSON
本体              manifest の files 順に連結
```

manifest:

```json
{
  "v": 1,
  "label": "screens",
  "root": "screens",
  "count": 3,
  "totalSize": 40213,
  "files": [
    { "path": "a.png", "size": 12345, "sha256": "…64 hex…" },
    { "path": "sub/b.txt", "size": 27, "sha256": "…" }
  ]
}
```

検証（受信側で必ず全部通す）:

1. magic と manifest 長が buffer に収まるか
2. JSON として妥当か、`v` が既知か
3. `count === files.length`、`totalSize === Σ size`
4. 本体の長さが `4 + 4 + manifestLen + totalSize` と一致するか
5. 各 `path` が相対パス検証を通るか（下記）
6. `path` の重複が無いか（大文字小文字を無視して比較）
7. 件数・総サイズ・個別サイズが上限内か
8. 各ファイルの SHA-256 が一致するか

相対パス検証で落とすもの:

- 絶対パス（`/x`, `\x`, `C:\x`, `C:x`）
- UNC（`\\server\share`）
- `..` を含むもの、`.` だけのセグメント
- 空セグメント（`a//b`）
- 制御文字、`:` `*` `?` `"` `<` `>` `|`
- Windows 予約名（`CON` `PRN` `AUX` `NUL` `COM1`–`COM9` `LPT1`–`LPT9`、拡張子付きも）
- 末尾がドットまたは空白のセグメント
- セグメント長 255 超、全長 1024 超

シンボリックリンクは **バンドルに入れない**（送信側で除外し、件数を報告する）。
受信側はファイル以外を作らないので、リンクが復元されることはない。

### 5.2 `DCS1` 一枚読みモード（2次元コードリーダー用）

連続映像ではなく、人が 1 枚ずつ読ませる前提。**別モード**として設計する。

HID ウェッジのリーダーはデコード結果を **キーストロークとして打つ**ので、
枠はテキスト安全でなければならない。バイナリ QR は使えない。

```
DCS1|<docId>|<idx>|<total>|<crc32hex>|<base64url payload>
```

- `docId` — 8 hex。別の文書のフレームが混ざるのを防ぐ
- `idx` / `total` — 10 進。順不同で構わない
- `crc32hex` — payload（base64url を戻したバイト列）の CRC-32、8 hex
- 受信側は `(docId, idx)` で重複排除し、CRC 不一致は捨てる
- 全 `idx` が揃ったら連結して `DCF2` コンテナとして展開、SHA-256 検証

**普通の1次元バーコードリーダーは対応済みとしない。** 文書にもそう書く。

### 5.3 中継 API（Tailscale 上）

| メソッド | パス | 用途 |
|---|---|---|
| `POST` | `/api/v1/pair` | ペアリングコード → デバイストークン発行 |
| `GET` | `/api/v1/hello` | ホスト名・版・登録済み受信ルート一覧 |
| `GET` | `/api/v1/outbox` | 送信待ち一覧（id・名前・件数・サイズ） |
| `GET` | `/api/v1/outbox/{id}` | バンドル本体 |
| `POST` | `/api/v1/inbox/{routeId}` | バンドル本体を受け取り保存 |

認証と整合性:

- ペアリング: ホスト側でローカルに生成した **6 桁 + チェック文字**のコードを
  発行（既定 10 分・1 回限り）。スマホがコードを送ると、ホストが
  デバイス ID と 32 byte の共有秘密を返す。
- 以後の要求は `Authorization: Decimen <deviceId>` に加え、
  `X-Decimen-Timestamp`、`X-Decimen-Body-Sha256`、
  `X-Decimen-Signature = HMAC-SHA256(secret, method \n path \n timestamp \n bodySha256)`。
- タイムスタンプの窓は ±120 秒。窓外は拒否。
- 本体の SHA-256 はヘッダと突き合わせ、受信後に再計算して比較。

listen:

- 既定で **Tailscale インターフェイスのアドレスにのみ bind**。
- Tailscale アドレスが見つからない場合は **起動しない**。理由を表示して失敗する
  （0.0.0.0 への暗黙のフォールバックはしない）。
- 明示的に別アドレスへ bind したい場合は設定に書く必要があり、その場合は
  起動ログと `status` に警告を残す。

## 6. 安全性の要件と対応

| 脅威 | 対応 |
|---|---|
| パストラバーサル | `relative-path.ts` で送受両側。受信側が最終判断 |
| 絶対パス・UNC・ドライブ | 同上 |
| Windows 予約名 | 同上（`CON.txt` も落とす） |
| シンボリックリンク | 送信時に除外し件数を報告。受信は通常ファイルしか作らない |
| 過大サイズ／件数 | manifest の宣言値と実測の両方を上限と突き合わせ |
| gzip 爆弾 | 上流の `gunzipAsync` の出力上限をそのまま使う |
| 壊れたフレーム | QR の CRC＋`parseFrame` の妥当性検査。噴水側は欠落として吸収 |
| 途中欠落 | 噴水符号（連続モード）／`idx` 集合の欠番検出（低速モード） |
| 重複フレーム | `seq` の `seen` 集合（連続）／`(docId, idx)`（低速） |
| ハッシュ不一致 | バンドル全体と各ファイルの二段。**不一致は保存しない** |
| 黙った上書き | 既定は重複名回避（`name (2).ext`）。上書きは明示操作のみ |
| 受信物の自動実行 | 一切実行しない。開く操作も提供しない（フォルダを開くのみ） |
| ログからの漏洩 | パスは相対パスのみ、本文とトークンは書かない |
| 設定不備の黙認 | 不備は理由を表示して失敗。機能を黙って落とさない |
| 不用意な listen | Tailscale アドレス以外へは明示設定が無い限り bind しない |

## 7. UI / UX

### 7.1 design token の作り方

MacroStudio / App Studio の**実物の GUI と実装**を読み、次を抽出して
この製品用の token に落とす（画面構造はコピーしない）。

- 色: 明るいキャンバス＋白いカード、藍色のアクセント 1 本、
  成功／警告／危険はそれぞれ 1 色。暗い配色も同じ意味名で持つ
- 文字: 3 段（title / body / meta）＋数値表示 1 段。強調は太さと色で、サイズを増やさない
- 余白: 4px 刻みの 8 段
- 角丸: 2 種類 + pill
- 影: 2 段
- 寸法: 行高・ボタン高・トップバー・アクションバーなどを token 化

### 7.2 画面の原則（先生の一貫した要求）

1. 1 画面 = 1 目的 = 1 主操作。一本道
2. 送る／受け取る／設定の現在地、進行、完了、エラー、復旧方法が見て分かる
3. token は 2〜3 段。その場限りの強調を作らない
4. 実行 / 単一選択 / 複数選択 / モード切替 / 任意入力 / 詳細表示は見た目を分ける
5. グレーアウトは「操作不能」だけ。任意項目には使わない
6. 詳細は折り畳んでよいが、存在と辿り方は隠さない
7. トグルは現在の状態と切り替え後に変わることを、文言と視覚の両方で示す
8. 内部プロトコル用語（噴水符号・k・seq・FNV）は通常画面に出さない
9. 画面切替で主要入力の位置を飛ばさない
10. デスクトップは横幅を使う。細い 1 カラムを延々スクロールさせない
11. PWA のスマホ幅は別レイアウト

### 7.3 画面一覧

**PC アプリ**（横幅を使う 2 カラム）

| 画面 | 主目的 | 主操作 |
|---|---|---|
| 送る | 選んだものを QR で流す | 「送信をはじめる」 |
| 受け取る | 画面／リーダーから受け取って保存する | 「カメラで受け取る」／「リーダーで受け取る」 |
| 設定 | 保存先・受信の既定・上限・診断 | 各設定 |

**スマホ PWA**（1 カラム、縦積み）

| 画面 | 主目的 |
|---|---|
| 中継トップ | いまできることを 2 つ示す |
| PC から受け取って流す | outbox を選ぶ → QR 表示 |
| 読み取って PC へ送る | カメラ受信 → 受信先を選んで送信 |
| 受信先 | ペアリングと登録済み一覧 |

## 8. 検証計画

「起動した」「DOM がある」「API が返った」では完了にしない。

### 8.1 自動テスト

| 種別 | 内容 |
|---|---|
| 上流維持 | 既存 74 件をそのまま通す |
| 単体 | 相対パス検証（悪意ある入力を網羅）、バンドル pack/parse、上限、SHA 不一致 |
| ゴールデン | `DCB1` と `DCS1` を固定バイト列に固定する |
| 低速モード | 欠落・順不同・重複・CRC 破損・別文書混入 |
| 中継 | 署名・改竄・期限切れ・リプレイ・トークン誤り・ペアリング再使用 |
| 保存 | 重複名回避、明示上書き、検証失敗時に何も残さない |
| E2E（実バイト） | 送信 → バンドル → 光学符号化 → 復号 → 保存 のバイト一致 |
| E2E（中継） | headless 受信先へ実際に送って保存されたバイトを比較 |
| E2E（カメラ） | Playwright の fake media（QR 列から生成した Y4M）でカメラ経路を通す |
| リーダー | COM / キーボードウェッジをエミュレートして一枚読み受信を通す |

### 8.2 実 GUI

- 実際に `pc/decimen.bat` から WPF + WebView2 アプリを起動する
- 実際のコントロールを操作して主要フローを完走する
- 主要状態を **実画面からキャプチャー**して `evidence/` に保存する
  - 標準 Windows サイズ / 狭いウィンドウ / 125% 相当 / 代表的スマホ幅
  - 通常・転送中・カメラ許可要求・拒否・カメラなし・破損・再開・完了
- 文字切れ、重なり、見切れ、不要スクロール、空白、密度、フォーカス、
  ボタンの到達性、QR 表示領域を目で見て評価し、直して撮り直す

### 8.3 この環境で確認できないもの

正直に書き、人間用の受入手順を残す:

- 物理スマホでの PWA 実行
- 物理ノート PC の内蔵カメラ
- 物理 2次元コードリーダー
- 実 Tailscale の複数端末

先生のデスクトップにはカメラが無いので、**「カメラなし」の実状態は本物で確認**し、
**受信成功は fake camera で確認**する。実カメラ未確認はそう明記する。
