### skip した 3 件と、その理由

skip は全て**理由つき**で出ます。黙って通るものはありません。

| テスト | 理由 |
|---|---|
| `a folder crosses the optical channel and lands on disk byte for byte` | この環境の Chromium / WebView2 が擬似カメラを提供しない（`getUserMedia` が `NotFoundError`）。実行前に実際に問い合わせて判定している |
| `a link already sitting in the destination is not followed` | Windows でシンボリックリンクを作るには開発者モードか昇格が要る |
| `a destination that cannot be written to is reported before a transfer starts` | Windows の読み取り専用属性はフォルダーへの作成を止めないため、この確認は POSIX のみ |

### 特に確かめたこと

**実バイト一致まで見ているもの**

- `optical-loop.test.ts` — フォルダー → バンドル → SHA-256 → 噴水符号 →
  QR 描画 → **製品と同じ zxing での実復号** → 噴水復号 → コンテナ検証 →
  バンドル検証 → **元のバイトと一致**。24 KB の非圧縮データで **26 枚以上を
  実際に復号**していることも検査に入れてある（1 枚で収まる標本では噴水符号を
  一度も通らないため）
  - 3 枚に 1 枚を落としても完走
  - 画面を横切る帯で潰したフレームを混ぜても完走
  - 逆順に投入しても同じバイト列
- `relay-e2e.test.ts` — **実 HTTPS サーバー**に実署名で送り、**実フォルダーに
  書かれたバイト**を元と比較

**攻撃を模したもの**

- 悪意あるパス 37 種（traversal / 絶対 / ドライブ相対 / UNC / 円記号 /
  NTFS 副ストリーム / 予約名 / RLO / ゼロ幅 / 末尾ドット）
- manifest の数値細工（負・小数・`1e999`・安全整数超・文字列・null）
- 宣言 manifest 長を buffer 外へ、末尾に余分なバイト、途中で切る
- 署名後の本体改竄 → 400、**何も書かれない**
- 要求の再送 → 2 回目は 401
- 他端末の id での署名、別パスへの署名の流用 → 401
- 登録コードの総当たり 5 回 → **コードが破棄され、正しいコードも通らなくなる**
- 他サイトからの呼び出し → 403（ペアリングは常に拒否）

## 3. 実 GUI の操作

### デスクトップアプリ

`pc\pub-transfer.ps1 -DebugPort 9333` で**実際にアプリを起動**し、DevTools
プロトコルで**実ウィンドウの実コントロール**を操作しました
（`tools/drive-desktop.ts`）。ブラウザーに複製したページではありません。

通した流れ:

1. 入口 →「送る」
2. **実フォルダーを実際に走査**（3 ファイル・1.2 KB）し、件数・合計・所要目安を表示
3. 「送信をはじめる」→ **実バンドル生成 → 実 QR ストリームを実画面に表示**
   （51 枚まで表示されたことを画面上で確認）
4. 「表示を終わる」→「表示を終わりました」（**完了とは言わない**）
5. 設定 → 保存先・呼び名・2 つのトグル・読み取り機
6. 「受け取る」→ 受け取り方の選択（**このマシンは本当にカメラが無い**）
7. カメラなし / カメラ拒否 の実状態
8. 「読み取り機で 1 枚ずつ読む」→ **実 `DCS1` フレーム 12 枚**を入力
   （2 枚を意図的に飛ばし、`あと 2 枚 ── 3, 6` の名指し表示を確認）
9. 残り 2 枚を補う → **照合成功 → 中身を確かめて保存**の画面へ到達
10. 狭いウィンドウ（900×680）で 2 カラムが 1 カラムに落ちること
11. 表示倍率 125% 相当（1092×614 CSS px）での 3 画面

**ページのコンソールに出たエラー: なし。**

### スマホ PWA

**実 relay ホスト**（実 HTTPS サーバー・実証明書・実署名・実ペアリング）に
対し、3 つの実機相当幅で同じ流れを通しました（`tools/drive-phone.ts`）。

- 375×667（iPhone SE 相当）
- 412×915（Android 標準相当）
- 320×568（いちばん狭い実機相当）

表示終了 → カメラ経路 → カメラ拒否 → 渡す先の選択。

## 4.5 レビューで見つかり、直したもの

実装後に**コードそのもの**を別のレビューへ出し、14 件の指摘を全て直しました。
詳細と理由は [REVIEW-RESPONSE.md](REVIEW-RESPONSE.md) の C 節。実害の大きかった
順に 5 つ:

1. **失効が取り消されていた。** 認証のたびに端末情報を書き戻していたため、別の
   ターミナルで行った `device revoke` が数ミリ秒後に上書きされていた。しかも
   端末が動いている最中に上書きされる — 失効させたい状況そのもの
2. **`serve` が片方のアドレスでしか待ち受けていなかった。** 1 つの Server に
   2 回 listen していて 2 本目が例外。実ログで見つけ、実機で 2 本の Listen を
   確認するところまで直した
3. **nonce を署名の検証前に消費していた。** 端末 id は秘密ではないので、それだけ
   で本物の要求を「二重送信」にできた
4. **上限超過の 413 が届いていなかった。** ソケットを破棄していたので、相手には
   ECONNRESET しか見えていなかった
5. **TS と C# のパス検証が食い違っていた。** コメントが参照していた照合テストが
   存在しなかったので実装したところ、その場で孤立サロゲートの食い違いを検出した
   （`tests/path-parity.test.ts` は実際に C# をコンパイルして 56 種を突き合わせる）
