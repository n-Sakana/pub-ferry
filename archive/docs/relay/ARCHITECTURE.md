# 構成と脅威境界

対象: この fork が上流（`bashalarmistalt/decimen-optical-transfer` v0.3.0）へ足した部分。
上流の光学エンジンそのものは [architecture](../technical/architecture.md) と
[protocol](../technical/protocol.md) を参照。

---

## 1. 全体像

```
┌──────────── 内側（Tailscale の中）────────────┐   ┌──── 外側 ────┐
│                                               │   │              │
│  Windows デスクトップ  ─┐                     │   │  Windows PC  │
│  Windows ノート       ─┼─ relay ホスト        │   │  （中継なし） │
│  Linux VPS           ─┘   （Node, HTTPS）     │   │              │
│                            ▲                  │   │      ▲       │
└────────────────────────────┼──────────────────┘   └──────┼───────┘
                             │ Tailscale                   │ 光（QR）
                             │ + 署名つき HTTP             │
                        ┌────┴───────────────────────────┬─┘
                        │  スマートフォン（PWA / 中継器）  │
                        └────────────────────────────────┘
```

**内側の PC / VPS** は relay ホストを動かす。役割は 2 つだけ:
受け取り先（route）と、送信待ち（outbox）。

**スマホ**は中継器。両側に触れる唯一の端末で、したがってこの構成でいちばん
価値の高い標的でもある（§5）。

**外側の PC** は Tailscale に入らない。光学経路しか持たない。

**PC のデスクトップアプリは内側・外側で同じもの**。内側で使うときは
relay ホストも一緒に動かす、というだけの違い。

## 2. 層と、どこに何があるか

| 層 | 実体 | 置き場所 |
|---|---|---|
| 起動口 | `pub-ferry.bat`（薄い） | `pc/pub-ferry.bat` |
| 起動・構成・ビルド・ログ | PowerShell | `pc/pub-ferry.ps1` |
| OS 統合・ウィンドウ・保存 | C#（WPF + WebView2） | `pc/src/*.cs` |
| 画面 | 共有 TS/CSS | `pc/app/`, `relay/web/` |
| 共有コア | TypeScript | `shared/` |
| 受信ホスト | Node | `relay/` |

参照した 2 製品（MacroStudio / App Studio）と同じ層分けにしてある。
どちらのリポジトリも読み取りのみで、変更していない。

### 2.1 なぜ画面をホストが配信するのか

WebView2 の `SetVirtualHostNameToFolderMapping` は `WebResourceRequested` より
下の層で解決されるため、マップした仮想ホストへの要求はハンドラに届かない
（実測: `fetch` が `Failed to fetch` になり、ハンドラのログは 1 行も出なかった）。
そこで **仮想ホストのマッピングを使わず、C# がページのファイルそのものを配信**
している。結果として:

- ページとホストサービスが同一オリジンになり、CORS の問題が構造的に消える
- 応答ヘッダー（CSP を含む）がこちらの管理下に入る
- ページが読むバイト列は 1 か所を通る

### 2.2 なぜスマホのページを受信ホストが配信するのか

ブラウザは https のページから http を呼べず、Tailscale のアドレスは
「安全な生成元」に含まれない。**他所で配信されたページは受信ホストの API を
呼べない。** 受信ホスト自身が配信すれば同一生成元になり、この問題は消える。
ペアリングの秘密も、ただ 1 つのホストの生成元の下にだけ保存される。

複数ホストを 1 つのページから使いたい場合は、各ホストの設定
`allowedAppOrigins` に相手の生成元を明示的に書く（既定は空 = 同一生成元のみ）。

## 3. データの形

### 3.1 上流の形は変えていない

フォルダー一式は **`DCB1` というペイロード**であって、新しいフレーム形式では
ない。上流の `packFile(name, type, bytes)` に
`application/vnd.decimen.bundle+dcb1` として渡すので、20 バイトのフレーム
ヘッダーも噴水符号も `DCF2` コンテナも 1 バイトも変わっていない。上流の
ゴールデンベクタは全て通ったままである。

```
DCB1  4B magic
u32   manifest 長（little-endian）
      manifest（UTF-8 JSON: v / label / count / totalSize / files[] / skipped）
      本体（manifest の順に連結）
```

### 3.2 一枚ずつ読むモード `DCS1`

```
DCS1-<docId 6>-<index>-<total>-<CRC32 8桁>-<base32 payload>
```

英大文字・数字・ハイフンだけ。これは 2 つの制約の交わりである:

1. キーボードウェッジ型のリーダーは読み取り結果を **キー入力として打つ**。
   打たれた文字は OS のキーボードレイアウトを通るので、US 配列で Shift の要る
   記号は JIS 配列のホストで別の文字になる。この字種はどちらの配列でも
   非 Shift キーであり、Caps Lock で反転しても大文字化して読み戻せる。
2. 同じ字種が QR の **英数字モード**そのもので、2 文字を 11 ビットに詰められる。
   base32 の 1.6 倍を英数字モードが 1.45 倍取り返すので、バイトモードとの差は
   1 割程度に収まる。

CRC は **行全体**（枚数と番号を含む）に掛ける。ペイロードだけに掛けると、
番号が化けたフレームが「正しいブロックを誤った位置に」入り、最後の SHA-256 で
初めて落ちる。行全体なら、その場で撥ねられる。

### 3.3 ページ → C# ホストの `DCW1`

検証済みのファイル群を保存させるための、ホスト内だけの形式。
`DCW1` + u32 見出し長 + JSON（label / files[path,size]）+ 本体。
C# 側は **パスを再検証してから**書く。ページの言うことは信じない。

## 4. 脅威境界

```
┌─ 光学経路 ─────────────────────────────────────────────┐
│ 誰でも見える。暗号化されていない。                      │
│ 相手が読めたかどうかは分からない（一方通行）。          │
└────────────────────────────────────────────────────────┘
        │ 受け取った側は「知らない相手からのバイト列」として扱う
        ▼
┌─ 受信側の検証（順序が本体）───────────────────────────┐
│ 0. DCF2 の SHA-256                                     │
│ 1. DCB1 の構造（magic / 長さ / 数値の範囲）            │
│ 2. パス 1 本ずつ                                       │
│ 3. パス集合（重複・ファイルとフォルダーの衝突）        │
│ 4. 各ファイルの SHA-256                                │
│ 5. ここで初めて書き込み                                │
└────────────────────────────────────────────────────────┘
```

### 4.1 何を防いでいるか

| 脅威 | 対応 | 実装 |
|---|---|---|
| パストラバーサル | `..` セグメント、絶対パス、ドライブ相対、UNC を拒否 | `relative-path.ts` / `03_SafePath.cs` |
| 円記号によるプラットフォーム差 | `\` を含むパスは全て拒否（区切りは `/` のみ） | 同上 |
| NTFS 副ストリーム（`a.txt:secret`） | `:` を禁止文字に含める | 同上 |
| 予約デバイス名（`CON.txt` 等） | 拡張子を除いた先頭部分で照合 | 同上 |
| 表示偽装（RLO・ゼロ幅） | Cf 系文字を拒否 | 同上 |
| 正規化違いによる同名衝突 | NFC 以外を拒否 | 同上 |
| 大文字小文字違いの同名衝突 | 不変小文字化で衝突鍵を作る | `findPathSetConflict` |
| ファイルとフォルダーの名前衝突 | 集合として検査 | 同上 |
| 階層の過剰 | 32 段まで | `MAX_PATH_DEPTH` |
| 数値の細工（負・小数・巨大） | 使う前に安全整数と上限を検査 | `bundle.ts` |
| 長さの食い違い | 宣言長と実測長の**両方**を突き合わせ | 同上 |
| 途中に既にあるリンク（junction） | 解決後のパスを保存先と比較。リンクは拒否 | `writer.ts` / `04_SafeWriter.cs` |
| 既存ファイルの黙った上書き | 常に新しいフォルダーへ。`CREATE_NEW` で開く | 同上 |
| 半端な書き込みの残留 | 保存先の中に staging → 成功時に rename、失敗時に丸ごと削除 | 同上 |
| 受信物の自動実行 | 何も実行しない。フォルダーを開くだけ | `05_HostServices.cs` |
| 受信物の出所が不明なこと | Windows では Mark of the Web を付ける | `04_SafeWriter.cs` |
| gzip 爆弾 | 上流の出力上限をそのまま使う | 上流 `protocol.ts` |
| 欠落・重複・順不同フレーム | 噴水符号（連続）／`(docId, index)` 集合（低速） | `fountain.ts` / `slow-frames.ts` |
| 破損フレーム | QR の ECC ＋ フレーム妥当性 ＋ 行全体の CRC | `protocol.ts` / `slow-frames.ts` |
| 未登録端末からの書き込み | ペアリング必須。tailnet にいるだけでは権限にならない | `relay-auth.ts` |
| 総当たり | 10 文字 × 30 種（約 49 ビット）／10 分／5 回失敗でコード破棄 | 同上 |
| 改竄 | 本体 SHA-256 を署名に含め、受信後に再計算して比較 | `server.ts` |
| 再送 | nonce ＋ 時刻窓（±120 秒）＋ 使用済み nonce の保持 | 同上 |
| 巨大な本体 | 署名検証 → Content-Length 検査 → 読み込み、の順 | 同上 |
| 他サイトからの呼び出し | 未知の Origin は拒否。ペアリングは同一生成元のみ | 同上 |
| 端末紛失 | 端末側から解除、ホスト側から `device revoke` | `cli.ts` |
| 不用意な listen | Tailscale のアドレスにだけ bind。無ければ起動しない | `net.ts` |
| 秘密の漏洩 | `state.json` は 0600。ログにトークン・パス・本文を書かない | `store.ts` |

### 4.2 何を守らないか（非目標）

- **内容の秘匿性。** 光学経路は暗号化されていない。画面に出ているものは、
  その場のどのカメラからも読める。**この製品が与える性質は「network が
  間に無いこと」であって、秘匿ではない。** 覗かれて困るものを、覗ける場所で
  表示しないこと。
- **相手が受け取ったことの保証。** 画面 → カメラは一方通行で、戻りの経路が
  無い。送信側は「表示を終わった」ことしか言えない。UI もそう書いてある。
- **スマホ本体の防御。** スマホは両系統に触れる唯一の端末で、そこが乗っ取ら
  れれば、その端末に登録された受信先へ書き込める。緩和は、端末登録を最小限に
  すること、受信ルートを狭いフォルダーに限ること、失った端末をすぐ
  `device revoke` すること。**この設計はスマホを信頼している。**
- **tailnet 内の他ノードからの到達。** Tailscale の既定 ACL は全ノード全ポート
  許可なので、bind するだけでは「その port に触れるのは自分だけ」にはならない。
  ペアリングが実際の関門であり、加えて ACL でこの port を絞ることを
  [SETUP.md](SETUP.md) で求めている。
- **差分同期・削除伝播・競合解決。** 一回転送のツールであって同期ソフトでは
  ない。

## 5. 大きさと時間の現実

形式の上限（64 MB）と、実際に通る大きさは別物である。既定の上限は **16 MB**。

- **時間**: 上流の 128 KB/s は近距離のスマホ同士の値。机越しのモニターでは
  その一部しか出ない。64 MB は最良でも 9 分、実際には 20〜40 分。
- **記憶**: 中継するのはスマホである。受信側は解いたブロック・組み立てた
  コンテナ・`unpackFile` の切り出し・`digest()` の複製を同時に持つ。64 MB では
  モバイルのタブで 250〜350 MB になり、タブが落ちる。
- **再開できない**: 復号器はメモリ上にしかない。タブが背面に回れば全部消える。

したがって画面は、始める前に所要時間の目安を出し、上限を超える選択を
理由つきで拒否する。

## 6. 参照した 2 製品との関係

MacroStudio と App Studio は **読み取りのみ**で参照した。取り込んだのは方向性:

- BAT は薄い起動口、PowerShell が起動・構成・ビルド・ログ、C# が OS 統合、
  Web 側に共有 TS/CSS
- WebView2 の境界を 1 クラスに閉じ込め、そこを通らない経路を作らない
- 明るいキャンバス＋白いカード、アクセント 1 色、3 段の文字、4px の余白格子、
  角丸 2 種、影 2 段
- 「グレーは操作不能だけ」「色だけで意味を運ばない」

**取り込んでいないもの**: 画面構成、コンポーネント一式、色の実値。この製品の
token は [`shared/design/tokens.css`](../../shared/design/tokens.css) に
独自に書いてある。
